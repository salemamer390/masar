# Attendance import lineage and exception review

- Imported source is stored as encrypted database values, not a public file. Day punches and revisions require attendance.view. The source-sheet route additionally requires attendance.edit and renders mapped attendance columns only, never unassigned cells or metadata. The complete encrypted source has no display/download route. Company isolation applies to every model and route binding.
- A batch retains the selected source sheets, column mapping and options, and parsing errors. A day retains all original punches with source row references. Corrections change only current punches; originals and revisions cannot be changed through application routes or normal model writes; these are model hooks, not database triggers, and privileged direct SQL is outside that guarantee. Batch and audit tables have no deletion endpoint. Deliberate company-data retention/export/purge is a separate administrative workflow, not a side effect of deleting a punch.
- Temporary upload tokens expire after 30 minutes. Hourly cleanup removes expired/corrupt metadata plus companion files and old orphan workbook files. Permanent source and audit records are not pruned by that job.
- More than two punches creates a pending exception and no daily attendance write. If a daily record already exists it is explicitly shown as unchanged until review, not counted as an overwrite. A single punch remains incomplete and is marked pending. Explicit manual selection of check-in and check-out is needed to resolve a day. All times include dates; a next-day check-out is accepted only for an overnight span, not silently reassigned.
- Review needs attendance.view. Correction needs attendance.edit, plus attendance.create when it creates a daily record. Deleting a day or removing a punch needs attendance.delete. If a correction makes an existing daily record pending, removing that old daily record also needs attendance.delete. Existing attendance updates require an explicit overwrite checkbox.
- Both payroll finalization and attendance archive closure are checked inside the write transaction, under the company lock. Closed periods remain view-only. Exception review does not change automatic closing policy. Attendance displays a pending-exception warning before closing; archive snapshots retain the pending count in settings.
- Source parse errors with an unresolved employee/date remain in the batch original view, not invented employee-day exceptions. Correct the source and re-import those rows. No name-only identity matching or guessed employee/date is performed.
- Reimporting the same daily date updates attendance only after explicit confirmation; each import retains its own source batch for audit. It does not erase previous batches.
- No employee-destroy route exists in the current application (only profile-photo deletion). New employee/company foreign keys restrict hard deletion to preserve history; a future deletion workflow must handle this explicitly, not cascade away lineage.

- Required migration: 2026_11_04_000001_create_attendance_import_lineage.php. Existing APP_KEY must be backed up and kept stable because private source and revision data use application encryption. Migration was tested only against the isolated test database; production execution is not part of this change.

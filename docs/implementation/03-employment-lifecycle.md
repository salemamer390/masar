# المرحلة 3: الحركات الوظيفية والعقود

**الحالة:** منفذة جزئيًا  
**تاريخ التنفيذ:** 7 أكتوبر 2026

## النطاق المنفذ

تطوير سجل الحركات الوظيفية بحيث يحتفظ بالسياق الكامل للتغيير، وليس فقط بالأعمدة المنفصلة للقسم والوظيفة والراتب.

## ما نُفذ

1. أُضيفت migration `2026_10_07_000000_add_snapshots_to_movement_records` ونُفذت بنجاح في batch 5.
2. أضيفت حقول إلى `movement_records`:
   - `reason`: سبب الحركة.
   - `old_values` و`new_values`: snapshots JSON للقيم قبل وبعد التغيير.
   - `attachment_path`: مكان مرفق الحركة للاستخدام في خطوة إدارة المستندات.
   - index على `movement_date` لتحسين سجل الحركات والتقارير.
3. أصبح `MovementRecord` يدعم الحقول الجديدة والتحويل JSON.
4. عند إنشاء حركة، يحفظ النظام الحالة السابقة والجديدة للقسم والوظيفة والراتب.
5. يضاف Audit Log إضافي يحمل القيم السابقة والجديدة للحركة.

## التحقق

- فحص PHP للـ controller وmodel وmigration ناجح.
- `php artisan migrate --pretend` نجح قبل التطبيق.
- `php artisan migrate --force` نجح؛ migration مسجلة في batch 5.

## تحديث: خدمة الحركة الذرية

تم إنشاء `MovementService` ونقل منطق تنفيذ الحركة إليه. أصبحت العملية التالية داخل `DB::transaction` واحدة:

1. قفل سجل الموظف المعني لمنع التحديثات المتنافسة.
2. إنشاء سجل الحركة مع Snapshot قبل/بعد.
3. تحديث القسم والوظيفة الحالية للموظف.
4. عند تغيير الراتب: أرشفة الهيكل السابق، إنشاء/تحديث هيكل راتب بتاريخ سريان الحركة، ومزامنة الأجر التأميني.
5. كتابة Audit Log للقيم قبل/بعد.

إذا فشلت أي خطوة، يتراجع كل ما سبق في المعاملة ولا يبقى الموظف أو الراتب أو سجل الحركة في حالة جزئية. أصبح `MovementController` مسؤولًا فقط عن validation والاستجابة للواجهة.

**تحقق إضافي:** `php -l` للخدمة والـ controller ناجح، ومسارا الحركات GET/POST ما زالا ظاهرين في Laravel routes.

## أعمال متبقية

- ربط حقول السبب والمرفق بواجهة الحركات مع رفع ملف خاص ومحمي.
- استكمال أنواع الحركات: المدير، الفرع، نوع العقد، الحالة، التجديد، وإنهاء الخدمة.
- إنشاء جدول تاريخ العقود والتنبيهات الآلية لانتهاء العقد وفترة التجربة.
